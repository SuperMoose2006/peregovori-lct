# Диалог — материалы для промежуточной сдачи ЛЦТ, задача №9

Это содержание комплекта, а не готовая презентация. Ничего не опубликовано.
Официальный шаблон требует сохранить структуру обязательных слайдов 7–11;
персоналии и история команды должны прийти от владельца. Проверки и долги —
в [checklist](REQUIREMENTS_CHECKLIST_12206.md), вопросы —
в [списке владельцу](OWNER_QUESTIONS_12206.md).

## Концепция

«Диалог» — браузерная практика деловых переговоров для начинающих менеджеров,
сотрудников закупок/продаж и участников учебных программ. Пользователь
тренирует вопросы об интересах, объективные критерии, обмен условиями,
работу с возражениями и закрытие сделки. Организатор задаёт учебный контекст.

В лекции можно узнать название приёма, но нельзя увидеть последствия своей
реплики. Здесь реплика меняет доверие, напряжение, информацию и позицию
оппонента. После партии человек получает разбор и может переиграть решение.
Пользовательская эффективность в реальной работе пока не измерена; это
гипотеза продукта, а не результат проведённого исследования.

## Путь пользователя и организатора

1. Организатор открывает «Своя ситуация», описывает переговоры и раскрывает
   настройки. Поля: сфера, тема, роль/цель оппонента, сложность 1–5 и тон.
2. Сеть/модель доступна — генерируется сценарий; без сети работает обозначенный
   шаблон. Сложность и тон применяются непосредственно к сценарию движка.
3. Игрок видит задачу и условия, ведёт переговоры текстом или доступным голосом.
4. Движок определяет последствия и исход. Практика может использовать
   семантического ИИ-судью; зачётные режимы работают без него и без слоёв.
5. Разбор показывает исход, составляющие оценки, удачные и слабые ходы.
   Доступны курс, повтор, «А что если…», чтение чужой партии и смена стороны.

Настройки организатора — часть существующего интерфейса, без отдельной
учётной записи администратора и без разграничения ролей. Это граница MVP.

## Техническая часть

React/TypeScript → WebSocket → FastAPI → оркестратор → движок переговоров.
Сценарии содержат роли, скрытые интересы, диапазон сделки и сложность.
Движок считает состояние и итог; модели помогают интерпретировать довод,
формулируют ответ и разбор. Голос и камера — адаптеры, не источники баллов.

Офлайн-зеркало движка в TypeScript проверяется общими фикстурами с Python.
Вопрос «Читай лицо» онлайн создаёт сервер по реакции после судьи/apply_move,
офлайн — локальное ядро. Десять форм курса валидируются строгими схемами.

Лицо в текущем MVP — состояния портрета, без lip-sync и без настоящего
микродвижения. OpenTalking в отдельном интерфейсе не является интеграцией.
Локальный ASR на стенде управляется systemd; облачный fallback остаётся
возможным при отказе службы. Перезагрузка всего хоста не проверялась.

## Локальный запуск для жюри

Нужны Python с venv, Node/npm и современный Chrome. Версии использованного
окружения и результаты — в отчёте проверок; новый чистый Python venv этой
ночью не устанавливался. Перед публичным показом проверять именно машину
показа по [плейбуку](demo.md).

```bash
python3 -m venv services/gateway/.venv
services/gateway/.venv/bin/pip install -r services/gateway/requirements.txt
npm --prefix frontend ci
npm --prefix frontend run build
```

Далее из `services/gateway`:

```bash
NEGO_AI=off .venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8010
```

Открыть `http://127.0.0.1:8010`. Для облачного варианта задать ключ в
игнорируемом `services/gateway/.env`: `OPENROUTER_API_KEY` (совместимое имя
`OPENAI_API_KEY`), затем перезапустить без `NEGO_AI=off`. Значения ключей не
включать в презентацию, архив или историю команд. Точные роли моделей — в
README и `docs/model-bakeoff.md`; текущее включение проверять health/preflight.

Встроенные сценарии, курс и локальные партии доступны без платного ключа.
Настоящий облачный сценарий и речь без ключа не обещаются. Для спокойного
демо иметь открытый встроенный стол «Контракт с поставщиком» и резервную
офлайн-партию. Прогресс хранится в браузере, серверные активные партии в RAM.

## Демонстрация на 3–4 минуты

- **0:00–0:35:** настройки своей ситуации. Показать сферу «Промышленность»,
  тему «Годовая поставка», роль «Директор завода», цель «Сохранить объём»,
  сложность и тон. Объяснить офлайн-ограничение, если сеть недоступна.
- **0:35–1:40:** переговоры на встроенном столе. Вопрос об интересах, затем
  аргумент с критерием. Сравнить с пустым перечислением приёмов, если живой
  судья заранее проверен. Не обещать фиксированное решение облачной модели.
- **1:40–2:30:** финальный разбор: исход сделки, доверие, техника и конкретный
  ход. Для гарантированного финала использовать проверенную эталонную партию
  из `frontend/test/fixtures/games.json`, а не импровизированное обещание A.
- **2:30–3:20:** упражнение курса и «Чтение стола». Показать связь правильного
  ответа с той же механикой, что использовалась в партии.
- **3:20–4:00:** архитектура, офлайн-резерв и честные границы: портрет без
  lip-sync, отсутствие внешнего доказательства эффективности обучения.

## Текст для обязательного шаблона

### Слайд 7 — титул

Диалог. Тренажёр деловых переговоров. Задача №9 — ОЭЗ «Алабуга».
Название команды и логотип постановщика заполнить из согласованных данных.

### Слайд 8 — описание и уникальность

**Суть:** практика переговоров с управляемым контекстом и разбором последствий
каждой реплики. Организатор настраивает задачу, игрок проходит партию и учится
на конкретных решениях.

**Особенность:** состояние и оценку считает движок; семантический ИИ помогает
разбирать аргумент и говорить от лица оппонента. Курс и офлайн-режим проверены
на общей механике. Это свойство реализации; превосходство над всеми
конкурентами не заявляется.

Капитан, размер/история команды, город/регион — нужны данные владельца.

### Слайд 9 — участники

Для каждого: имя/фамилия, роль, место работы/учёбы, контакт в мессенджере,
телефон в согласованном владельцем объёме. Данные не установлены; не выдумывать.

### Слайд 10 — история, выбор задачи, сложности

Историю команды и мотивацию выбора задачи заполнит команда. Подтверждённая
техническая сложность: семантическая оценка ИИ может колебаться; зачётный режим
изолирован от судьи и дополнительных слоёв. Ещё один пример: ручной ASR не
переживал рестарт хоста; добавлен systemd, устранён отказ кэша Numba и проверено
распознавание после рестарта службы. Эти примеры не подменяют личную историю.

### Слайд 11 — техническая и продуктовая суть

**Техническая:** React/TypeScript + FastAPI/WebSocket, отдельный движок,
модальные адаптеры и офлайн-зеркало; общие фикстуры и полный регрессионный набор.

**Применение:** короткие тренировки перед переговорами и организованные
учебные занятия. Следующий шаг — пилот с наставником и заранее заданными
критериями улучшения навыка; коммерческий спрос/продажи пока не измерены.

## Дорожная карта до финала

| Этап | Результат и критерий приёмки | Зависимость |
|---|---|---|
| Перед промежуточной сдачей | Заполненный официальный шаблон, воспроизводимый локальный запуск, два полных сценария и демонстрация настроек | Реквизиты команды, среда сборки PPTX, проверка машины показа |
| Стабилизация демонстрации | Прогон живого текста/голоса/камеры и контроль fallback; по согласованному окну reboot ASR | Доступ/окно стенда, ключи; без изменения движка |
| Лицо оппонента | Реальный видеопровайдер: синхронизация с тем же звуком, отмена, fallback; проверка записи аудио+кадров | Провайдер/GPU/модель и разрешённый бюджет |
| Микродвижения | Согласованные клипы по состояниям, контроль идентичности, reduced-motion и fallback | Готовый контент или производство |
| Пользовательская проверка | Пилот с заранее описанной рубрикой, сравнение до/после и отчёт об ограничениях | Участники и эксперт, согласие на исследование |
| После доказанного спроса | Серверные попытки/сертификат, кабинет организатора, сохранение сценариев | Отдельная архитектурная задача; не рискованный ночной рефакторинг |

Duix и полный «мозг оппонента B» остаются исследовательскими вариантами,
не обязательством сроков. Даты подачи и финала сверить по текущим сообщениям
организаторов перед отправкой; этот worktree ничего не отправляет наружу.
