# Развёртывание: стенд, выкатка, откат, три линии кода и план их совмещения

Что стоит на публичном стенде, как выкатывать и откатывать, почему в проекте три линии кода и как их свести в одну.

Сокращения: SPA — одностраничное веб-приложение; SW — Service Worker, фоновый скрипт браузера для офлайн-кэша; ASR — распознавание речи.

Секреты, адрес входа по SSH, имя пользователя и путь к ключу здесь намеренно не приводятся. Они в передаточной записке команды (основной репозиторий, `SPEC_LCT_HANDOFF.md`, §3) и в `docs/DEPLOY_12206.md`.

## 2. Как выкатывать

Скрипты выкатки (`pack-release.sh`, `activate-release.sh`, `Caddyfile`, `dialog.service`, `check-public.py`) живут на линии стенда. **В ветке аудита из `deploy/` есть только юнит `dialog-asr.service`.**

```bash
# 1. локально, на линии стенда
npm --prefix frontend run build
bash deploy/pack-release.sh /tmp/dialog-release-<ID>   # каталог обязан быть НОВЫМ, frontend/dist — существовать
tar -czf /tmp/dialog-release-<ID>.tar.gz -C /tmp dialog-release-<ID>
shasum -a 256 /tmp/dialog-release-<ID>.tar.gz
# 2. скопировать архив в /opt/dialog/ на сервере, сверить хеш, распаковать в /opt/dialog/releases/<ID>,
#    собрать окружение: uv venv --python 3.13 и pip install -r requirements.txt -c requirements.lock
# 3. активировать
bash /opt/dialog/releases/<ID>/deploy/activate-release.sh /opt/dialog/releases/<ID>
```

`activate-release.sh`: атомарно переключает ссылку `current`, перезапускает **только** `dialog`, 30 раз с интервалом в секунду спрашивает `/api/health` и при неудаче сам возвращает прежний релиз. `pack-release.sh` отказывается упаковывать ссылки, `.env`, `.pem`, `.key` и пишет манифест SHA-256 файлов.

**Грабли, на которые уже наступали:**
- SSH к стенду рвётся на длинных командах — долгое запускать через `nohup setsid … &` и читать лог.
- Изменить существующий файл в `/etc` можно, создать новый — только человеком.
- Один worker обязателен: партии живут в памяти процесса. `--forwarded-allow-ips=127.0.0.1` не убирать: приложение отличает локальные запросы от внешних по IP.
- Не поднимать лимит памяти шлюза ради модели распознавания: 5,7 ГБ модели в процессе шлюза уронят партии.
- Старый пользователь видел прежнюю сборку в открытой вкладке; помогал `Cmd+Shift+R`. Заголовки кэша в Caddy не проверялись.

## 3. Как откатывать

```bash
bash /opt/dialog/releases/<предыдущий ID>/deploy/activate-release.sh /opt/dialog/releases/<предыдущий ID>
```

Старые релизы не удаляются: это весь механизм отката. Для нынешнего стенда точка возврата — `20260923-b682bb4`. **Предусловия отката проверены (файлы, окружение, скрипт на месте), сам обратный откат ни разу не исполнялся.** Возврат серверной ссылки не обновляет кэш браузера: вкладка с зарегистрированным SW может держать новые ресурсы — это часть приёмки любой будущей выкатки.

**Происхождение стендовой линии подтверждено объектами Git**, а не названием релиза: `b682bb4` — слияние 23.09 с родителями `b80abda` и `fb8b498`; от общей базы изменено 95 файлов, из них 75 во `frontend` и `services/gateway/app`. Сообщение слияния прямо описывает совмещение двух параллельных сессий. Побайтово с Git совпали все 70 файлов `services/gateway/app` на сервере (`docs/INTEGRATION_PLAN_12206.md`).

## 5. План совмещения: база — стенд, переносится смысл исправлений

План `docs/INTEGRATION_PLAN_12206.md` подготовлен 26.09 и **не применён** — ждёт слова владельца. Прямая замена стенда архивом ветки аудита отвергнута: она удалила бы «Редактор», значки и другие рабочие функции.

**Основа — `b682bb4`.** Патч исправлений аудита не накладывается в восьми файлах (`git apply --check`); решение по каждому:

| Файл | Решение |
|---|---|
| `frontend/build/offline.ts`, `frontend/vite.config.ts`, `frontend/tsconfig.node.json` | оставить стендовый сборщик офлайн-кэша; не держать два |
| `frontend/public/sw.js` | стендовые фильтры и проверку ответа сохранить; отдельно обеспечить, чтобы старая открытая вкладка находила свои ресурсы, а офлайн-страница бралась из текущей версии |
| `frontend/package.json` | вручную согласовать с lock-файлом, затем чистая установка — **это же чинит падение `npm ci`** |
| `frontend/src/api/ws.ts` | оставить стендовую реализацию жизненного цикла; перенести только тест D1 |
| `frontend/src/components/CourseScreen.tsx` | сохранить значки; перенести смысл D6 и D8 с тестами |
| `frontend/src/i18n.ts` | оставить стендовый словарь (ключи «Редактора», значки) |

Вне этих восьми: D7 в `frontend/src/realtime/transport.ts`; правки `App.tsx` по смыслу; не объявлять работающими неподключённые `admission.py` и `sessionStore.ts`; тестовые каталоги не заменять целиком.

**Порядок:** кандидат в собственной ветке → бесплатная приёмка (проверка типов, сборка, оба набора тестов, «Редактор», значки, экспорт, D1–D8, две версии SW, обычное и истёкшее восстановление) → показ владельцу SHA, состава и протокола приёмки → **выкатка отдельным решением**, откат штатным скриптом на `b682bb4`.

| Вариант | Что делаем | Цена |
|---|---|---|
| **план** | кандидат по плану, автоматическая приёмка, выкатка потом | ориентир 1–2 инженерных дня (SW и `App.tsx` — самое дорогое) |
| **стенд** | оставить `b682bb4` на показ, исправления держать локально | ноль работы; D3, D4, D6, D7, D8 остаются на стенде |
| **минимум** | перенести только D3, D4, D6, D7, D8 и согласовать lock | 0,5–1 дня плюс регрессия |

**Чего план не покрывает.** Линия «Встречи» появилась после плана и строится поверх `master`. Если её берут в показ, её надо включить в кандидата: она меняет оформление целиком, путь хода голосом и клиентскую обработку поколений.

## 6. Перед показом

```bash
make preflight         # шлюз жив, ключ на месте, судья включён, процесс отвечает свежим кодом
make preflight-live    # то же плюс один настоящий ход живой моделью
make preflight-layers  # то же плюс живой голос и живое зрение (платно: голосовой ход — 4 обращения к моделям)
```

Флаги целям `make` не передаются: `make preflight --live` перехватит сам `make`, напечатает справку и выйдет с нулём, ничего не сделав. Аргументы — через `ARGS=`. Физические микрофон и наушники проверяются человеком по `docs/VOICE_MANUAL_12206.md` за две минуты.
