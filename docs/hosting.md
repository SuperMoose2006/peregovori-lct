# Показ по сети: почему сертификат обязан быть настоящим

Тренажёр просит микрофон и камеру. Это «мощные возможности» браузера, и они
живут не в HTTPS вообще, а в **доверенном** HTTPS. Разница не косметическая, и
она измерена.

## Что ломает самоподписанный сертификат

Первый показ стоял на `https://185.154.194.88:8443` с самодельным сертификатом.
Замер (`frontend/probes/`) на этом хосте:

```
защищённый контекст: true
service worker: НЕТ
ошибок: 1 — «An SSL certificate error occurred when fetching the script»
```

Контроль на `http://127.0.0.1:8010` (доверенный origin без сертификата вовсе):
service worker **зарегистрирован**. Значит дело не в коде и не в самом файле —
браузер отказывает именно этому происхождению.

Service worker — только видимая часть. `window.isSecureContext` возвращает
`true` и после того, как человек прощёлкал предупреждение, поэтому по этому
флагу ничего не видно; но происхождение с ошибкой сертификата остаётся
«ненадёжным», и на телефонах (в первую очередь Safari на iOS) запрос
`getUserMedia` на нём отклоняется без вопроса пользователю. Голосовой и
камерный слои на демонстрации просто не включаются, а офлайн-оболочка не
ставится.

Вывод короткий: **самоподписанный сертификат — это не «HTTPS с предупреждением»,
это половина продукта.**

## Что стоит сейчас

```
https://185-154-194-88.nip.io        (порт 443, без порта в адресе)
логин dialog · пароль в NEGO_HTTP_PASSWORD
```

Домена у стенда нет, есть только адрес. `nip.io` разрешает
`185-154-194-88.nip.io` в `185.154.194.88`, а Let's Encrypt выдаёт на такое имя
обычный сертификат. Проверка HTTP-01 занята: порт 80 держит посторонний
контейнер, трогать его нельзя. Поэтому проверка идёт по TLS-ALPN-01 на 443 —
её умеет `acme.sh`, но не `certbot`.

Замер на этом хосте, тем же прибором:

```
защищённый контекст: true
service worker: зарегистрирован
getUserMedia: ok:video · ok:audio
кадров ушло: 19 · зрение ответило: «В кадре отсутствует человек…»
ошибок: 0
```

## Выпуск и продление

Состояние acme.sh лежит в `/root/.acme.sh` (не в репозитории — там ключ).

```bash
# выпуск
/root/.acme.sh/acme.sh --home /root/.acme.sh \
  --issue --alpn --tlsport 443 -d 185-154-194-88.nip.io --server letsencrypt

# продление: 443 обязан быть свободен на время проверки, значит гейтвей
# останавливается, продлевается сертификат, гейтвей поднимается снова
/root/.acme.sh/acme.sh --home /root/.acme.sh --renew --alpn --tlsport 443 \
  -d 185-154-194-88.nip.io --ecc
```

Срок текущего — до 24 ноября 2026, окно продления открывается 24 октября.

**Продление РУЧНОЕ.** Обычно acme.sh ставит себе задание в cron сам; здесь
`crontab -l` пуст, а значит никто не продлит сертификат за вас, и в один день
демо просто перестанет открываться. Проверить срок:

```bash
openssl x509 -in services/gateway/certs/le-fullchain.pem -noout -dates
```

Файлы копируются в `services/gateway/certs/` (каталог в `.gitignore`):

```bash
S=/root/.acme.sh/185-154-194-88.nip.io_ecc
cp $S/fullchain.cer services/gateway/certs/le-fullchain.pem
cp $S/185-154-194-88.nip.io.key services/gateway/certs/le-key.pem
chmod 600 services/gateway/certs/le-key.pem
```

## Запуск

```bash
cd services/gateway && set -a && . ./.env && set +a && \
  PYTHONPATH=/root/LCT ./.venv/bin/uvicorn app.main:app \
    --host 0.0.0.0 --port 443 \
    --ssl-keyfile certs/le-key.pem --ssl-certfile certs/le-fullchain.pem
```

**Перезапуск после правок кода.** Шлюз — долгоживущий процесс: он держит в
памяти тот код, с которым поднялся. Однажды процесс, раздававший демо, крутился
двое с половиной суток и отвечал позавчерашним кодом — курс на диске знал
упражнение, живой процесс нет. `/api/health` отдаёт отпечаток (сколько
упражнений, столов, кампаний), и `make preflight` сверяет его с диском; но
проверять надо ПОМНИТЬ, поэтому правило простое: правили бэкенд — перезапустите
процесс.

```bash
kill $(ss -ltnp | grep ':443 ' | grep -o 'pid=[0-9]*' | cut -d= -f2)
# затем команда запуска выше
```

Фронтенд перезапуска не требует: статику шлюз читает с диска, достаточно
`npm run build`.

Пароль берётся из `NEGO_HTTP_PASSWORD` в `.env`. Пусто — вход открыт;
задан — внешние запросы просят пароль, локальные (OpenTalking, приборы,
скриншоты) не трогаются. Веб-сокет пароля в заголовке не получает — браузер его
там не шлёт, — поэтому успешная проверка HTTP оставляет куку `dlg_ok`, и
`/v1/realtime` проверяет её.

## Что стенд отдавал наружу и почему это стоит перечитать

29 августа обстрел протокола нашёл в SPA-фолбэке обход каталога: `GET
/../../services/gateway/.env` возвращал 200 и содержимое — ключ OpenRouter. Тем
же запросом отдавался `/etc/passwd`. Дыра была открыта ровно столько, сколько
стенд смотрел в интернет.

**Ключ считается скомпрометированным.** Пароль на HTTP тут не защита: его знают
все, кому его назвали на показе, а ключ — не их. Ключ надо перевыпустить в
личном кабинете OpenRouter и заменить в `services/gateway/.env`; старый —
отозвать. Того же требует ключ OpenAI из `OPENAI_REALTIME_KEY`, если он лежал в
том же файле.

Проверка, что дыры нет (должно вернуться содержимое `index.html`, а не файла):

```bash
curl -s -u dialog:ПАРОЛЬ --path-as-is \
  'https://185-154-194-88.nip.io/../../services/gateway/.env' | head -c 40
```

Урок общий: **каталог со статикой — это граница доверия.** Путь приходит с
улицы, и проверять его надо после `realpath`, а не отсечением «..» в строке:
символьная ссылка внутри `dist` ведёт наружу без единой точки в пути.
