# Серверное свидетельство результата

Основание: новое поручение владельца через Jarvis 22 сентября — аттестация нужна,
результат должен считаться и подписываться сервером и иметь проверяемый ID.
Выбрана обратимая граница: одна анонимная экзаменационная партия, не прохождение
всего курса и не подтверждение личности/квалификации. Можно переиграть после
решения владельца. Порог A/B/C сохранён из существующего экзамена, формула,
баланс, движок и локальный курс не менялись.

## Путь доверия

1. Сервер при создании партии запоминает исходный режим и допустимость выдачи.
   Только exam на одном из девяти стандартных столов без присланной репутации.
   Resume не меняет исходный режим; практика не превращается в экзамен.
2. После завершения движок через views считает итог. Клиент не передаёт баллы,
   грейд, время выдачи или признак «сдано». Ручки выдачи по клиентскому JSON нет.
3. Для A/B/C сервер создаёт случайный 128-битный ID, UTC-время, область результата,
   версию методики и баллы. Канонический JSON аутентифицируется HMAC-SHA256.
   Это серверная криптографическая подпись для проверки реестром; не заявление
   о квалифицированной электронной подписи. Resume-token в документ не входит.
4. SQLite сохраняет документ и подпись; повторная выдача той же партии возвращает
   тот же ID. Публичный GET `/api/attestations/{id}` проверяет подпись перед ответом.
   Подмена БД, неподходящий ключ или сбой проверки не дают `valid: true`.
5. `/api/attestations/{id}/document` отдаёт автономный RU/EN HTML для печати,
   только после проверки подписи. Клиентское имя туда не попадает. Страница
   содержит ID и ссылку на проверку. Браузерный экран отдельно запрашивает реестр;
   локальный результат/локальный курс не выдаются за серверное свидетельство.

## Включение и хранение

По умолчанию выдача выключена. Для выбранного серверного процесса нужны:

- `NEGO_ATTESTATION_KEY`: отдельный случайный секрет, 32 байта в hex (64 символа).
  Передавать через защищённое окружение, не через браузер, git или командную строку.
- `NEGO_ATTESTATION_DB`: абсолютный путь к SQLite на постоянном диске, в заранее
  созданном каталоге с доступом только пользователя gateway. Каталог должен быть
  разрешён существующей systemd-песочницей; права и размещение согласовать при деплое.

Ключ и БД необходимо сохранять вместе вне каталогов релизов и резервировать.
Текущая версия обслуживает один ключ: простая замена ключа сделает прежние записи
непроверяемыми. Перед ротацией нужен key-id/keyring и миграционный план.
Производственный ключ ночью не создавался, конфигурация/релиз стенда не менялись.
Для локальной браузерной проверки использован временный реестр и случайный ключ
в памяти отдельного тестового gateway. Они удаляются по завершении прибора.

Политика сроков хранения НЕ выбрана: автоматического удаления нет. До согласования
не включать сбор реальных результатов. Нет удостоверения личности, ведомости
прохождения всего курса, защиты от помощи другого человека, отзыва свидетельств
или независимой проверки открытым ключом. Это явно ограничивает презентационную
формулировку: реализована проверяемая серверная основа, выпуск дипломов — будущий
этап после необходимых согласований, а не текущая возможность выдавать дипломы.
